Author
Affiliation

Vagish Hemmige

MAHV

Drafts the mapping of every USRDS primary-cause code to the six categories of the paper’s Table 1, using three cloud large language models. Codes on which at least two of the three agree are accepted without being read by a person; the deciders review the rest. Two smaller models that run on the analyst’s own computer answer the same question and are reported for comparison, but do not vote: neither produced a complete, valid set of answers (see What the local models showed). Whether a model-drafted mapping is acceptable for the replication at all is still an open decision (D4). This step comes after the public area data and before any USRDS data are loaded, and it uses none. Its line in R/main.R is commented out: the script is run once, by hand, because it calls paid APIs and needs the local models, and the file it writes to references/ is what the analysis reads once the deciders have reviewed it.

NoteWhat this step needs and produces

To run it, from the project root: source("R/setup.R"), source("R/functions.R"), then source("R/classify_esrd_causes.R"). It is not part of main.R.

It needs

  • ellmer 0.5.0 or later (Wickham et al., n.d.), and the irr package for Fleiss’ kappa.
  • An API key for each cloud provider in .Renviron: OPENAI_API_KEY, ANTHROPIC_API_KEY and GEMINI_API_KEY.
  • Ollama running on the same computer, with the two local models pulled (ollama pull qwen3.5:9b and ollama pull llama3.1:8b in a terminal). The script checks both before asking any model, and says what to do if either is missing. Ollama can take some work to set up; see Setting up Ollama before the first run.
  • The models, batch sizes and agreement rule set in setup.R (see Setup): gpt-6.1-terra (OpenAI), claude-sonnet-5-5 (Anthropic) and gemini-3.8-flash (Google) in the cloud, and locally, reported without voting, qwen3.5:9b (Alibaba’s Qwen) and llama3.1:8b (Meta’s Llama).

It sends only the public list of 445 codes with their descriptions: in batches of 100 to OpenAI and Claude (about five calls each), of 25 to Gemini and Qwen (about eighteen calls each), and of 5 to Llama (89 calls), plus more calls for any codes a model skipped. Gemini timed out on batches of 100, and local models are slower and handle less text at once: on the analyst’s laptop, Llama 3.1 answered only 7 codes of a batch of 25, but every code of a batch of 5. The local models send nothing over the internet. No patient data are sent anywhere. Each call starts a new conversation, and no temperature or seed is set, so a second run could give different answers; the saved answer files are the record of what each model said.

It produces

  • One file of checked answers per model, in the gitignored data-raw/ folder.
  • references/esrd-cause-categories.csv: one row per code, with each model’s category and reason, how the models agreed (agreement), the accepted category (final_category), the decider’s initials (reviewer), and the prompt version, ellmer version, models and date.
  • references/esrd-cause-agreement.csv: one row with the number of codes accepted unanimously, by majority only and not at all, and Fleiss’ kappa.
  • references/esrd-cause-local-models.csv: one row per local model, with how many codes it answered, left unanswered or answered with text that is not a code, and how often it agreed with the accepted category.

How the analysis uses it: Linking area data reads only code and final_category. It stops if any code lacks one of the six categories, and warns if cause codes in the data are missing from the file; codes not in the file count as Other.

Editing the file: the deciders fill final_category and reviewer for the codes with no majority, and for any accepted code they change. Edit it as text (in Positron, or another text editor), not in Excel: 11 codes start with a zero, which Excel would strip, and those patients would silently become Other.

ellmer version

ellmer asks Claude for its native structured output only for model names it recognizes, and it recognizes Claude 5 names such as claude-sonnet-5-5 from version 0.5.0 (the function has_claude_structured_output() in ellmer’s source). Older versions force a tool call instead, which current Claude models reject with the error “tool_choice … not supported for this model”.

Protecting the deciders’ review

Rerunning the script rewrites the mapping file. If the deciders have already reviewed any code in it, the script stops before calling any model, so their review cannot be overwritten; the existing file has to be renamed or moved first, and the reviewed rows copied into the new one.

Click to show/hide R Code 
# A rerun rewrites the mapping file. Stop before any API call if the deciders
# have already reviewed codes in it, so their review is not overwritten.
if (file.exists(esrd_cause_mapping_file)) {
  existing_mapping <- read_csv(
    esrd_cause_mapping_file,
    col_types = cols(.default = col_character())
  )
  # Files written before the `reviewer` column held the deciders' initials in
  # `reviewed_by`, beside the models' "unanimous" and "2 of 3 models"
  reviewed_codes <- if ("reviewer" %in% names(existing_mapping)) {
    filter(existing_mapping, !is.na(reviewer))
  } else {
    filter(
      existing_mapping,
      !is.na(reviewed_by),
      !str_detect(reviewed_by, "^unanimous$|of \\d+ models$")
    )
  }

  if (nrow(reviewed_codes) > 0) {
    stop(str_glue(
      "{esrd_cause_mapping_file} has {nrow(reviewed_codes)} code(s) reviewed by the deciders. ",
      "Rename or move it before rerunning, then copy the reviewed rows into the new file."
    ), call. = FALSE)
  }
}

The code list

The original mapping spreadsheet is lost. Its replacement starts from a public list: every code of USRDS format $PD96DET with its description, from Appendix C of the Researcher’s Guide (United States Renal Data System 2024), which usRds already holds. There are 445 codes: 128 ICD-10-CM codes from the 2015 form, and 317 older codes, mostly ICD-9-CM codes (many with a letter added by USRDS) plus a few that mean the cause is missing. No patient data are involved, and the list is not filtered by what appears in the data. (The original spreadsheet was built from the codes that appeared in the data.) The script stops if a code is listed twice.

Click to show/hide R Code 
# usRds holds Appendix C internally; usRds:::metadata_c is used until the
# package exports the formats (to be raised in the usRds project). The
# **OTHER** row is the format's catch-all for unlisted values, not a code.
cause_codes <- usRds:::metadata_c[["PD96DET"]] |>
  transmute(
    code = str_trim(as.character(value)),
    description = str_squish(as.character(description))
  ) |>
  filter(code != "**OTHER**")

# A code listed twice would be classified twice; stop rather than keep one
duplicated_codes <- cause_codes |>
  count(code) |>
  filter(n > 1)

if (nrow(duplicated_codes) > 0) {
  stop(str_glue(
    "$PD96DET lists {nrow(duplicated_codes)} code(s) more than once: ",
    "{str_flatten_comma(duplicated_codes$code)}."
  ), call. = FALSE)
}

The prompt

All five models, voting or not, receive the same prompt, word for word. It is kept as a text file, prompts/esrd-cause-classification.md, so that it can be read and edited on its own and shown here exactly as sent:

You are a nephrologist classifying the primary cause of kidney failure recorded on the CMS-2728 Medical Evidence form, using the USRDS code list.

Assign each code to exactly one of these categories:

- Diabetes: kidney failure attributed to type 1 or type 2 diabetes, including diabetic nephropathy and diabetes with renal manifestations.
- Hypertension and cardiac disease: hypertensive kidney disease and nephrosclerosis, hypertensive heart and kidney disease, renovascular and other large-vessel disease of the kidney (renal artery stenosis, occlusion or thrombosis, renal atheroembolism), and kidney failure attributed to heart disease, such as cardiorenal syndrome or heart failure.
- Glomerulonephritis: primary and secondary glomerular disease. Primary includes IgA nephropathy, focal segmental glomerulosclerosis, membranous nephropathy, membranoproliferative glomerulonephritis, and acute, rapidly progressive or chronic nephritic and nephrotic syndromes. Secondary includes glomerulonephritis caused by systemic disease: lupus nephritis, ANCA-associated vasculitis (granulomatosis with polyangiitis or Wegener's granulomatosis, microscopic polyangiitis, polyarteritis), anti-GBM disease (Goodpasture's syndrome) and Henoch-Schönlein purpura. It also includes infection-related glomerular disease: post-infectious glomerulonephritis, HIV-associated (AIDS) nephropathy, glomerulonephritis associated with hepatitis B or C, and cryoglobulinemic glomerulonephritis. Thrombotic microangiopathies (hemolytic-uremic syndrome, thrombotic thrombocytopenic purpura), scleroderma, and lupus described as tubulointerstitial disease are not in this category.
- Hereditary or polycystic kidney disease: polycystic kidney disease and other inherited kidney diseases, including medullary cystic disease, Alport syndrome, Fabry disease, cystinosis, primary oxalosis and tuberous sclerosis. Congenital anomalies that are not described as inherited (renal hypoplasia or dysplasia, congenital obstruction) are not in this category.
- Transplant failure or complications: complications or failure of any transplanted solid organ or of bone marrow.
- Other: any cause that fits none of the five categories above. This includes:
  - other kidney and urinary tract disease: interstitial nephritis, pyelonephritis and other kidney or urinary tract infections (including renal tuberculosis), obstructive and urologic disease, congenital anomalies that are not inherited, and acute kidney injury;
  - systemic disease that is not glomerulonephritis: thrombotic microangiopathies, scleroderma, neoplasms (including myeloma and amyloidosis);
  - codes meaning that the cause is missing, unknown or unreconcilable.

Classify from the code and its description only; do not assume information that is not given.
Return one entry per code, with the code exactly as given and a reason of at most 15 words.

Codes:
{{code_list}}

For each batch, {code_list} becomes one line per code: the code, a colon and the USRDS description from the Researcher’s Guide (for example, 4464Z: WEGENERS GRANULOMATOSIS). Nothing else about a code is sent. The script stops if the prompt does not define each of the six categories, under exactly the names in setup.R, because the structured output can only return those names.

The prompt makes three rules:

  • One category per code, from the six in the paper’s Table 1, each defined in words.
  • “Other” is the catch-all, for every cause outside the first five and for codes that mean missing, unknown or unreconcilable. This is an assumption: the original spreadsheet had a sheet named “Other”, but what it contained is not known.
  • No inference beyond the description. The model classifies from the code and its description only, which keeps it from inventing context.

The six categories

The original analysis took the six categories from a spreadsheet with one sheet per category (“Diabetes”, “Hypertensive and Cardiac”, “Glomerulonephritis”, “HereditaryPCKD”, “Transplant”, “Other”), which no longer exists. Only the categories’ names survive, in the sheet names and in the paper’s Table 1, which labels the transplant category “solid organ and bone marrow” (Hemmige et al. 2024).

The definitions in the prompt (decided by Vagish Hemmige, 27 October 2026) start from the 12 headings of the 2015 CMS-2728 list of primary causes (Centers for Medicare & Medicaid Services 2015) and depart from them where the clinical definition differs:

CMS-2728 heading (2015) Category here
Diabetes Diabetes
Glomerulonephritis Glomerulonephritis
Secondary Glomerulonephritis/Vasculitis Glomerulonephritis for lupus nephritis, ANCA vasculitis and Henoch-Schönlein purpura; Other for thrombotic microangiopathies (hemolytic-uremic syndrome, thrombotic thrombocytopenic purpura) and scleroderma
Interstitial Nephritis/Pyelonephritis Other
Transplant Complications Transplant failure or complications
Hypertension/Large Vessel Disease Hypertension and cardiac disease
Cystic/Hereditary/Congenital/Other Diseases Hereditary or polycystic kidney disease for cystic and inherited disease; Other for congenital anomalies not described as inherited
Neoplasms/Tumors Other
Disorders of Mineral Metabolism Other
Genitourinary System Other
Acute Kidney Failure Other
Miscellaneous Conditions Other, except heart failure (Hypertension and cardiac disease) and HIV disease (Glomerulonephritis)

The 2015 list covers only the ICD-10-CM codes. The older ICD-9-CM codes in $PD96DET are placed by the same definitions; anti-GBM disease (Goodpasture’s syndrome), for example, appears only among them and counts as glomerulonephritis.

Four departures need a reason:

  • Secondary glomerulonephritis is glomerulonephritis. The CMS list keeps it apart, but lupus nephritis, ANCA vasculitis and Henoch-Schönlein purpura are glomerular inflammation. Lupus described as tubulointerstitial disease is not, and goes to Other. Thrombotic microangiopathies and scleroderma kidney disease, in the same CMS heading, are injury to the small vessels and endothelium rather than glomerular inflammation, so they also go to Other.
  • Infection-related glomerular disease is glomerulonephritis: post-infectious glomerulonephritis, glomerulonephritis with hepatitis B or C, and cryoglobulinemic glomerulonephritis. Infections that are not glomerular, such as pyelonephritis and renal tuberculosis, stay in Other.
  • HIV-associated nephropathy is glomerulonephritis. The 2015 CMS list places HIV disease (code B20) under Miscellaneous Conditions (Centers for Medicare & Medicaid Services 2015). Clinically, HIV-associated nephropathy is a glomerular disease whose classic form is collapsing focal segmental glomerulosclerosis (Rosenberg et al. 2015), so here it counts as glomerulonephritis, a deliberate departure from the CMS grouping. On the first run, before the definitions were written, all three models put HIV in Other. Earlier versions of the prompt are in the repository’s history, and each saved answer file names the prompt version it answered.
  • Heart failure is cardiac disease. The sheet name “Hypertensive and Cardiac” suggests that kidney failure attributed to heart disease belonged with hypertension, so heart failure (I50.9, in Miscellaneous Conditions on the CMS list) counts there.

Transplant failure or complications. The paper’s Table 1 labels this category “solid organ and bone marrow”. On a first Medical Evidence form it mostly means kidney failure after a transplant of another organ (heart, liver, lung) or of bone marrow, for example from calcineurin-inhibitor toxicity. A failed kidney transplant would not usually start incident dialysis, since that patient already had kidney failure.

What the paper’s Table 1 can and cannot show. In the published cohort, the six categories were diabetes 48.0%, hypertension and cardiac disease 29.5%, glomerulonephritis 5.7%, hereditary or polycystic kidney disease 1.9%, transplant 0.5% and other 14.3% (computed from the Table 1 counts). Among all incident patients in 2016, glomerulonephritis was 7.3% and cystic kidney disease 2.8% (computed from the counts in Table 1.6 of the 2018 USRDS Annual Data Report (United States Renal Data System 2018)). The cohort is in-center hemodialysis only, and patients with glomerulonephritis or cystic kidney disease more often start on peritoneal dialysis or receive a transplant first (Table 1.6 (United States Renal Data System 2018)), so these percentages cannot show where the original spreadsheet drew either boundary. Small groups such as HIV are invisible in these percentages.

Prompt and schema in code

The structured output schema restricts each answer to the six category names. The check in this section confirms that the prompt defines each of them. Each saved answer file carries a short fingerprint of the prompt text, so an edited prompt is sent to every provider again; the fingerprint is also recorded in the mapping file.

Click to show/hide R Code 
# The prompt is the text file esrd_classifier_prompt_file (prompts/), shown in
# full on the website. It defines each category in words; {{code_list}} is
# filled in for each batch.
prompt_text <- read_lines(esrd_classifier_prompt_file)

# The structured output can only return names from esrd_cause_categories, so
# the prompt must define each of them under exactly that name
undefined_categories <- esrd_cause_categories |>
  discard(\(category) any(str_starts(prompt_text, str_glue("- {category}:"))))

if (length(undefined_categories) > 0) {
  stop(str_glue(
    "{esrd_classifier_prompt_file} has no definition line ",
    "(\"- <category>: ...\") for: {str_flatten_comma(undefined_categories)}."
  ), call. = FALSE)
}

classification_prompt <- function(batch) {
  ellmer::interpolate_file(
    esrd_classifier_prompt_file,
    code_list = str_flatten(str_c(batch$code, ": ", batch$description), "\n")
  )
}

# A short fingerprint of the prompt text, ignoring Windows line endings. It is
# part of each saved answer file's name, so editing the prompt asks every
# provider again instead of reusing answers to the old prompt.
prompt_version <- prompt_text |>
  str_remove_all("\r") |>
  rlang::hash() |>
  str_sub(1, 8)

classification_type <- ellmer::type_array(
  ellmer::type_object(
    code = ellmer::type_string("The code exactly as given"),
    category = ellmer::type_enum(esrd_cause_categories, "Cause of kidney failure category"),
    reason = ellmer::type_string("Reason, at most 15 words")
  )
)

One function per model

Five models, set in setup.R, three voting and two reported, all called through ellmer (Wickham et al., n.d.) with the same structured output. Each model has its own function, so each can be run, checked and saved on its own. Claude’s answers are capped at 4,096 tokens by default in ellmer, too few for 100 codes with reasons, so its limit is raised (esrd_classifier_claude_max_tokens).

The three cloud models are each provider’s current general-purpose model. The two local models run through Ollama on the analyst’s computer (decided by Vagish Hemmige, 28 October 2026): Alibaba’s Qwen and Meta’s Llama, from two further companies. They were chosen to vote, and were moved to reporting only on 29 October 2026 (decided by Vagish Hemmige), when neither produced a complete, valid set of answers. Qwen answers with its “thinking” turned off (reasoning_effort = "none"): with it on, its reasoning filled Ollama’s working space before it wrote the answer, and the answer was cut off. Llama 3.1 replaced IBM’s Granite (granite4.2:8b) on 29 October 2026 (decided by Vagish Hemmige): on the analyst’s laptop Granite timed out after 30 minutes on a batch of 25 codes, and returned no answers for 5 codes in 15 minutes. Ollama’s models trained for medicine were considered, but they are all Google’s MedGemma, which would overlap with Gemini, or older models built on Llama 2. Both local models are small enough to run on a laptop. They show the approach that would be needed if a classification ever involved patient data: a model on the analyst’s own computer sends nothing to an outside company. Here only the public code list is used, so the cloud models are allowed, and the local models show what that approach costs.

Click to show/hide R Code 
# One function per model. Each takes a batch of codes and returns one row per
# code with code, category and reason, through ellmer's structured output.
# Each call starts a new chat, so no batch sees another batch's answers.
ask_openai <- function(batch) {
  chat <- ellmer::chat_openai(model = esrd_classifier_models$openai, echo = "none")
  chat$chat_structured(classification_prompt(batch), type = classification_type)
}

ask_google <- function(batch) {
  chat <- ellmer::chat_google_gemini(model = esrd_classifier_models$google, echo = "none")
  chat$chat_structured(classification_prompt(batch), type = classification_type)
}

ask_anthropic <- function(batch) {
  chat <- ellmer::chat_anthropic(
    model = esrd_classifier_models$anthropic,
    params = ellmer::params(max_tokens = esrd_classifier_claude_max_tokens),
    echo = "none"
  )
  chat$chat_structured(classification_prompt(batch), type = classification_type)
}

# The two local models run through Ollama (http://localhost:11434), in the
# same way; ask_ollama() returns the function for one of them, with any
# settings it needs (passed to ellmer::params())
ask_ollama <- function(model, ...) {
  function(batch) {
    chat <- ellmer::chat_ollama(model = model, params = ellmer::params(...), echo = "none")
    chat$chat_structured(classification_prompt(batch), type = classification_type)
  }
}

providers <- list(
  openai = ask_openai,
  anthropic = ask_anthropic,
  google = ask_google,
  # Qwen's "thinking" off (see setup.R)
  ollama_qwen = ask_ollama(esrd_classifier_models$ollama_qwen, reasoning_effort = "none"),
  ollama_llama = ask_ollama(esrd_classifier_models$ollama_llama)
)

# A local model on a laptop processor can take longer than ellmer's default
# wait of 5 minutes per answer
options(ellmer_timeout_s = esrd_classifier_timeout_s)

Setting up Ollama

Ollama runs open-weight models on the analyst’s own computer, and ellmer talks to it with chat_ollama(). Its advantage is privacy: in Ollama’s words, “Ollama runs locally. We don’t see your prompts or data when you run locally” (Ollama FAQ). A cloud model, by contrast, receives every prompt on the provider’s servers. This step sends only the public code list, so the cloud models are allowed here, and the local models are a demonstration of the approach that text containing patient information would need. Whether a particular computer and setup are acceptable for protected health information is for the institution to decide, not something Ollama guarantees.

Two cautions about the privacy claim:

  • Ollama also offers cloud models, run on Ollama’s servers, and its cloud features are on by default. The models used here are local, but to rule out sending anything by mistake, Ollama can run in local-only mode: set the environment variable OLLAMA_NO_CLOUD=1 and restart Ollama; its log then shows Ollama cloud disabled: true (Ollama FAQ: disabling cloud features).
  • The models are downloaded from the internet (ollama pull), and Ollama checks for its own updates. Only the prompts and answers stay on the computer.

The disadvantage is setup. Ollama has to be installed, the models downloaded (5–8 GB each), and Ollama has to find a way to run them that works on that computer. On a computer without a capable graphics card the models run on the processor, which is much slower than the cloud models.

Steps

  1. Install Ollama from ollama.com/download. The Windows notes give the requirements and where Ollama keeps its files.
  2. Download the two models in a terminal: ollama pull qwen3.5:9b and ollama pull llama3.1:8b (Qwen 3.5, Llama 3.1). On a computer with less memory, qwen3.5:4b (3–4 GB) is a smaller choice; change its name in setup.R.
  3. Test each model in the terminal before running the script: ollama run qwen3.5:9b "Say hello". A model that cannot answer this will not answer the script either, and the terminal shows the error directly.
  4. Measure the speed: ollama run qwen3.5:9b --verbose "Say hello" prints, after the answer, an eval rate in tokens per second. A batch of 25 codes needs roughly 1,000 tokens of answer, so at 5 tokens per second a batch takes about 3 minutes and the 18 batches about an hour, per model. The first request after starting Ollama also loads the model from disk, which takes up to a minute. Qwen 3.5 “thinks” before it answers, which adds to the time (Ollama: thinking).

If a model crashes: the graphics card

Ollama looks for a graphics card and puts as much of the model on it as fits. If the card or its driver is not up to it, the model crashes while loading, and every model fails, including the smallest. This happened on the computer used for this project on 28 October 2026, a Windows laptop with an Intel Core i7-8850H, 32 GB of memory and a small NVIDIA Quadro P1000 graphics card (4 GB) beside the processor’s built-in graphics:

  • With Ollama 0.40.4 and 0.40.12, every model crashed with exit status 0xc0000005. The log showed the model being loaded onto CUDA0, the NVIDIA card.
  • Hiding the card from CUDA (below) made a different error appear, exit status 0xe06d7363. The log showed Ollama then using the same card through Vulkan, another way of reaching graphics cards, and ggml_vulkan: device lost on Vulkan0.
  • Turning off both made every model run, on the processor only.

Ollama’s hardware page says that NVIDIA cards of this generation (compute capability 5.0 to 6.2) need driver version 570 or newer, and the log reported a driver supporting CUDA 12.2, which points to an older driver. Updating the driver was not tried; the 4 GB card would hold only a small part of these models in any case.

To run on the processor only (Windows; type in a terminal, then quit Ollama from its icon by the clock, start it again, and open a new terminal):

setx CUDA_VISIBLE_DEVICES -1
setx OLLAMA_VULKAN 0

Both come from Ollama’s hardware page: an invalid card number such as -1 makes Ollama ignore NVIDIA cards, and OLLAMA_VULKAN=0 turns off Vulkan. CUDA_VISIBLE_DEVICES also hides the NVIDIA card from any other program that uses CUDA (machine-learning software, for example), though not from the screen, video or games. To undo either, delete it under “Edit environment variables for your account” in Windows (Ollama FAQ: environment variables on Windows).

Reading Ollama’s log. On Windows the logs are in %LOCALAPPDATA%\Ollama (paste that into the Windows Run box, Windows key + R); server.log is the newest and server-1.log and so on are older (Ollama troubleshooting). The lines that matter:

  • inference compute, near the start: what Ollama will use. library=cpu means the processor; library=CUDA or Vulkan means a graphics card.
  • load_tensors: ... model buffer size, when a model loads: where it was put (CPU, CUDA0, Vulkan0).
  • The last lines before Load failed: the actual error.

In a terminal, powershell -command "Get-Content $env:LOCALAPPDATA\Ollama\server.log -Tail 60" shows the end of the log.

Running, checking and saving each model

Before asking any model, the script checks that Ollama is running and has the local models that still need to be asked. While it runs, it reports each model, whether its answers are read from a saved file or asked for, each batch as it is sent, and how long the provider took. The voting models’ answers are checked on every run, whether they are new or read back from a saved file: every code answered exactly once, no invented codes, and only the six categories (check_votes(), on the functions page). The local models’ answers are kept as they came back, and are counted rather than checked (below). Local models get up to 30 minutes per answer (esrd_classifier_timeout_s); ellmer’s default of 5 minutes was too short on a laptop processor. Each batch’s answers are saved as soon as the batch finishes, in a partial file beside the provider’s answer file, so a rerun after a failure (a timeout, a daily quota, a computer going to sleep) asks only the codes that provider has not yet answered. When a provider finishes, its answers are saved under the provider, model and prompt version, and the partial file is deleted; a rerun then asks only the providers that have not finished. A saved file that no longer matches the code list, for example after a usRds update, stops the script; deleting that file asks the provider again.

Agreement

A code is accepted when at least two of the three cloud models agree, a majority rule chosen for this demonstration (decided by Vagish Hemmige, 29 October 2026; the rule was three of five while the local models voted). Accepted codes are not read by a person. agreement says, for each code, whether the models were unanimous, how many agreed (for example “2 of 3 models”), or that no category had a majority. For codes with no majority, the deciders fill final_category and their initials in reviewer.

Fleiss’ kappa describes how far the models agree beyond chance: 1 is perfect agreement and 0 is what chance alone would give. It is reported in the agreement summary, and is not used to accept or reject codes.

What the local models showed

The two local models were meant to vote, and were run on the analyst’s laptop (processor only, 32 GB of memory) on 28 and 29 October 2026. Neither produced a complete, valid set of answers, so neither votes (decided by Vagish Hemmige, 29 October 2026); their answers are kept and reported, because what they did is itself a finding of this demonstration.

  • They dropped codes in longer batches. Both answered every code of a 5-code test. In batches of 25, Qwen left 150 of the 445 codes unanswered even after asking a second time, and Llama answered 7 of a 25-code test. Even in batches of 5, Llama left 124 codes unanswered on its first pass, and 28 after asking a second time.
  • They returned text that is not a code. Qwen put 25 codes in quotation marks and returned one answer with no code. Llama returned codes with </code> attached, the placeholders {code} and What is the code?, four invented web addresses, and codes not in the list (for example Z88.0, and D1022 for E1022). In all, 20 of its answers carried text that is not a code in the list, and it answered 6 codes more than once, some with different categories.
  • Some categories contradict the model’s own reason or are clinically wrong. Qwen put AIDS nephropathy (429) under Diabetes, with the reason that it “falls under viral/glomerular causes … not diabetes”. Llama put lupus nephritis (7100) and membranous nephropathy (5831) under Diabetes, and malignant hypertension (4010) under Diabetes with the reason “No indication of diabetes”.
  • They were slow. Qwen took 108 minutes for its answers; Llama about 2.5 minutes per batch of 5, close to four hours for the list. The cloud models took minutes.
  • A third model did not run at all. IBM’s Granite (granite4.2:8b) timed out after 30 minutes on a batch of 25 codes, and returned no answers for 5 codes in 15 minutes; Llama replaced it.

These are observations from one laptop and one prompt, not a general verdict on local models; larger local models, a computer with a capable graphics card, or a prompt asking for fewer codes at a time might do better. references/esrd-cause-local-models.csv records, for each local model, how many codes it answered once with a code from the list, left unanswered or answered with other text, and how often it gave the category the cloud models accepted (local_model_report(), on the functions page).

How the mapping is checked

Agreement among the models shows only that they agree, not that they are right. The plan adds two checks on the data, run by an authorized person once the mapping is reviewed:

  • Against USRDS’s own grouping. The USRDS PATIENTS file carries a primary disease group for each patient (DISGRPC). A cross-tabulation of the six categories against it, as percentages with small cells suppressed, shows which codes the mapping puts somewhere USRDS does not. Differences are expected where the definitions depart from the CMS grouping on purpose (secondary glomerulonephritis, HIV, heart failure); any others point to codes to review.
  • Against the paper. The cohort’s share in each category, compared with the published Table 1 percentages above. A large gap in one category points to codes to review.

All five models, voting or not, receive the same prompt, word for word. It is kept as a text file, [`prompts/esrd-cause-classification.md`](https://github.com/VagishHemmige/Dialysis-facility-density-USRDS/blob/main/prompts/esrd-cause-classification.md), so that it can be read and edited on its own and shown here exactly as sent:

#| lang: markdown

For each batch, `{code_list}` becomes one line per code: the code, a colon and the USRDS description from the Researcher's Guide (for example, `4464Z: WEGENERS GRANULOMATOSIS`). Nothing else about a code is sent. The script stops if the prompt does not define each of the six categories, under exactly the names in `setup.R`, because the structured output can only return those names.

The prompt makes three rules:

-   **One category per code**, from the six in the paper's Table 1, each defined in words.
-   **"Other" is the catch-all**, for every cause outside the first five and for codes that mean missing, unknown or unreconcilable. This is an assumption: the original spreadsheet had a sheet named "Other", but what it contained is not known.
-   **No inference beyond the description.** The model classifies from the code and its description only, which keeps it from inventing context.

## The six categories

The original analysis took the six categories from a spreadsheet with one sheet per category ("Diabetes", "Hypertensive and Cardiac", "Glomerulonephritis", "HereditaryPCKD", "Transplant", "Other"), which no longer exists. Only the categories' names survive, in the sheet names and in the paper's Table 1, which labels the transplant category "solid organ and bone marrow" [@hemmige2024density].

The definitions in the prompt (decided by Vagish Hemmige, 27 October 2026) start from the 12 headings of the 2015 CMS-2728 list of primary causes [@cms2728_causes] and depart from them where the clinical definition differs:

| CMS-2728 heading (2015) | Category here |
|---|---|
| Diabetes | Diabetes |
| Glomerulonephritis | Glomerulonephritis |
| Secondary Glomerulonephritis/Vasculitis | Glomerulonephritis for lupus nephritis, ANCA vasculitis and Henoch-Schönlein purpura; Other for thrombotic microangiopathies (hemolytic-uremic syndrome, thrombotic thrombocytopenic purpura) and scleroderma |
| Interstitial Nephritis/Pyelonephritis | Other |
| Transplant Complications | Transplant failure or complications |
| Hypertension/Large Vessel Disease | Hypertension and cardiac disease |
| Cystic/Hereditary/Congenital/Other Diseases | Hereditary or polycystic kidney disease for cystic and inherited disease; Other for congenital anomalies not described as inherited |
| Neoplasms/Tumors | Other |
| Disorders of Mineral Metabolism | Other |
| Genitourinary System | Other |
| Acute Kidney Failure | Other |
| Miscellaneous Conditions | Other, except heart failure (Hypertension and cardiac disease) and HIV disease (Glomerulonephritis) |

The 2015 list covers only the ICD-10-CM codes. The older ICD-9-CM codes in `$PD96DET` are placed by the same definitions; anti-GBM disease (Goodpasture's syndrome), for example, appears only among them and counts as glomerulonephritis.

Four departures need a reason:

-   **Secondary glomerulonephritis is glomerulonephritis.** The CMS list keeps it apart, but lupus nephritis, ANCA vasculitis and Henoch-Schönlein purpura are glomerular inflammation. Lupus described as tubulointerstitial disease is not, and goes to Other. Thrombotic microangiopathies and scleroderma kidney disease, in the same CMS heading, are injury to the small vessels and endothelium rather than glomerular inflammation, so they also go to Other.
-   **Infection-related glomerular disease is glomerulonephritis**: post-infectious glomerulonephritis, glomerulonephritis with hepatitis B or C, and cryoglobulinemic glomerulonephritis. Infections that are not glomerular, such as pyelonephritis and renal tuberculosis, stay in Other.
-   **HIV-associated nephropathy is glomerulonephritis.** The 2015 CMS list places HIV disease (code B20) under Miscellaneous Conditions [@cms2728_causes]. Clinically, HIV-associated nephropathy is a glomerular disease whose classic form is collapsing focal segmental glomerulosclerosis [@rosenberg2015hivan], so here it counts as glomerulonephritis, a deliberate departure from the CMS grouping. On the first run, before the definitions were written, all three models put HIV in Other. Earlier versions of the prompt are in the repository's history, and each saved answer file names the prompt version it answered.
-   **Heart failure is cardiac disease.** The sheet name "Hypertensive and Cardiac" suggests that kidney failure attributed to heart disease belonged with hypertension, so heart failure (I50.9, in Miscellaneous Conditions on the CMS list) counts there.

**Transplant failure or complications.** The paper's Table 1 labels this category "solid organ and bone marrow". On a first Medical Evidence form it mostly means kidney failure after a transplant of another organ (heart, liver, lung) or of bone marrow, for example from calcineurin-inhibitor toxicity. A failed kidney transplant would not usually start incident dialysis, since that patient already had kidney failure.

**What the paper's Table 1 can and cannot show.** In the published cohort, the six categories were diabetes 48.0%, hypertension and cardiac disease 29.5%, glomerulonephritis 5.7%, hereditary or polycystic kidney disease 1.9%, transplant 0.5% and other 14.3% (computed from the Table 1 counts). Among all incident patients in 2016, glomerulonephritis was 7.3% and cystic kidney disease 2.8% (computed from the counts in Table 1.6 of the 2018 USRDS Annual Data Report [@usrds2018adr]). The cohort is in-center hemodialysis only, and patients with glomerulonephritis or cystic kidney disease more often start on peritoneal dialysis or receive a transplant first (Table 1.6 [@usrds2018adr]), so these percentages cannot show where the original spreadsheet drew either boundary. Small groups such as HIV are invisible in these percentages.

## Setting up Ollama {#setting-up-ollama}

[Ollama](https://ollama.com) runs open-weight models on the analyst's own computer, and ellmer talks to it with [`chat_ollama()`](https://ellmer.tidyverse.org/reference/chat_ollama.html). Its advantage is privacy: in Ollama's words, "Ollama runs locally. We don't see your prompts or data when you run locally" ([Ollama FAQ](https://docs.ollama.com/faq#does-ollama-send-my-prompts-and-answers-back-to-ollamacom)). A cloud model, by contrast, receives every prompt on the provider's servers. This step sends only the public code list, so the cloud models are allowed here, and the local models are a demonstration of the approach that text containing patient information would need. Whether a particular computer and setup are acceptable for protected health information is for the institution to decide, not something Ollama guarantees.

Two cautions about the privacy claim:

-   **Ollama also offers cloud models**, run on Ollama's servers, and its cloud features are on by default. The models used here are local, but to rule out sending anything by mistake, Ollama can run in local-only mode: set the environment variable `OLLAMA_NO_CLOUD=1` and restart Ollama; its log then shows `Ollama cloud disabled: true` ([Ollama FAQ: disabling cloud features](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features)).
-   **The models are downloaded from the internet** (`ollama pull`), and Ollama checks for its own updates. Only the prompts and answers stay on the computer.

The disadvantage is setup. Ollama has to be installed, the models downloaded (5–8 GB each), and Ollama has to find a way to run them that works on that computer. On a computer without a capable graphics card the models run on the processor, which is much slower than the cloud models.

### Steps

1.  **Install Ollama** from [ollama.com/download](https://ollama.com/download). The [Windows notes](https://docs.ollama.com/windows) give the requirements and where Ollama keeps its files.
2.  **Download the two models** in a terminal: `ollama pull qwen3.5:9b` and `ollama pull llama3.1:8b` ([Qwen 3.5](https://ollama.com/library/qwen3.5), [Llama 3.1](https://ollama.com/library/llama3.1)). On a computer with less memory, `qwen3.5:4b` (3–4 GB) is a smaller choice; change its name in `setup.R`.
3.  **Test each model in the terminal before running the script**: `ollama run qwen3.5:9b "Say hello"`. A model that cannot answer this will not answer the script either, and the terminal shows the error directly.
4.  **Measure the speed**: `ollama run qwen3.5:9b --verbose "Say hello"` prints, after the answer, an `eval rate` in tokens per second. A batch of 25 codes needs roughly 1,000 tokens of answer, so at 5 tokens per second a batch takes about 3 minutes and the 18 batches about an hour, per model. The first request after starting Ollama also loads the model from disk, which takes up to a minute. Qwen 3.5 "thinks" before it answers, which adds to the time ([Ollama: thinking](https://docs.ollama.com/capabilities/thinking)).

### If a model crashes: the graphics card

Ollama looks for a graphics card and puts as much of the model on it as fits. If the card or its driver is not up to it, the model crashes while loading, and every model fails, including the smallest. This happened on the computer used for this project on 28 October 2026, a Windows laptop with an Intel Core i7-8850H, 32 GB of memory and a small NVIDIA Quadro P1000 graphics card (4 GB) beside the processor's built-in graphics:

-   With Ollama 0.40.4 and 0.40.12, every model crashed with `exit status 0xc0000005`. The log showed the model being loaded onto `CUDA0`, the NVIDIA card.
-   Hiding the card from CUDA (below) made a different error appear, `exit status 0xe06d7363`. The log showed Ollama then using the same card through Vulkan, another way of reaching graphics cards, and `ggml_vulkan: device lost on Vulkan0`.
-   Turning off both made every model run, on the processor only.

Ollama's [hardware page](https://docs.ollama.com/gpu) says that NVIDIA cards of this generation (compute capability 5.0 to 6.2) need driver version 570 or newer, and the log reported a driver supporting CUDA 12.2, which points to an older driver. Updating the driver was not tried; the 4 GB card would hold only a small part of these models in any case.

**To run on the processor only** (Windows; type in a terminal, then quit Ollama from its icon by the clock, start it again, and open a new terminal):

```
setx CUDA_VISIBLE_DEVICES -1
setx OLLAMA_VULKAN 0
```

Both come from Ollama's [hardware page](https://docs.ollama.com/gpu): an invalid card number such as `-1` makes Ollama ignore NVIDIA cards, and `OLLAMA_VULKAN=0` turns off Vulkan. `CUDA_VISIBLE_DEVICES` also hides the NVIDIA card from any other program that uses CUDA (machine-learning software, for example), though not from the screen, video or games. To undo either, delete it under "Edit environment variables for your account" in Windows ([Ollama FAQ: environment variables on Windows](https://docs.ollama.com/faq#setting-environment-variables-on-windows)).

**Reading Ollama's log.** On Windows the logs are in `%LOCALAPPDATA%\Ollama` (paste that into the Windows Run box, Windows key + R); `server.log` is the newest and `server-1.log` and so on are older ([Ollama troubleshooting](https://docs.ollama.com/troubleshooting)). The lines that matter:

-   `inference compute`, near the start: what Ollama will use. `library=cpu` means the processor; `library=CUDA` or `Vulkan` means a graphics card.
-   `load_tensors: ... model buffer size`, when a model loads: where it was put (`CPU`, `CUDA0`, `Vulkan0`).
-   The last lines before `Load failed`: the actual error.

In a terminal, `powershell -command "Get-Content $env:LOCALAPPDATA\Ollama\server.log -Tail 60"` shows the end of the log.

## Running, checking and saving each model

Before asking any model, the script checks that Ollama is running and has the local models that still need to be asked. While it runs, it reports each model, whether its answers are read from a saved file or asked for, each batch as it is sent, and how long the provider took. The voting models' answers are checked on every run, whether they are new or read back from a saved file: every code answered exactly once, no invented codes, and only the six categories (`check_votes()`, on the [functions page](functions.qmd)). The local models' answers are kept as they came back, and are counted rather than checked (below). Local models get up to 30 minutes per answer (`esrd_classifier_timeout_s`); ellmer's default of 5 minutes was too short on a laptop processor. Each batch's answers are saved as soon as the batch finishes, in a partial file beside the provider's answer file, so a rerun after a failure (a timeout, a daily quota, a computer going to sleep) asks only the codes that provider has not yet answered. When a provider finishes, its answers are saved under the provider, model and prompt version, and the partial file is deleted; a rerun then asks only the providers that have not finished. A saved file that no longer matches the code list, for example after a `usRds` update, stops the script; deleting that file asks the provider again.

## Agreement

A code is accepted when at least two of the three cloud models agree, a majority rule chosen for this demonstration (decided by Vagish Hemmige, 29 October 2026; the rule was three of five while the local models voted). Accepted codes are not read by a person. `agreement` says, for each code, whether the models were unanimous, how many agreed (for example "2 of 3 models"), or that no category had a majority. For codes with no majority, the deciders fill `final_category` and their initials in `reviewer`.

Fleiss' kappa describes how far the models agree beyond chance: 1 is perfect agreement and 0 is what chance alone would give. It is reported in the agreement summary, and is not used to accept or reject codes.

## What the local models showed {#what-the-local-models-showed}

The two local models were meant to vote, and were run on the analyst's laptop (processor only, 32 GB of memory) on 28 and 29 October 2026. Neither produced a complete, valid set of answers, so neither votes (decided by Vagish Hemmige, 29 October 2026); their answers are kept and reported, because what they did is itself a finding of this demonstration.

-   **They dropped codes in longer batches.** Both answered every code of a 5-code test. In batches of 25, Qwen left 150 of the 445 codes unanswered even after asking a second time, and Llama answered 7 of a 25-code test. Even in batches of 5, Llama left 124 codes unanswered on its first pass, and 28 after asking a second time.
-   **They returned text that is not a code.** Qwen put 25 codes in quotation marks and returned one answer with no code. Llama returned codes with `</code>` attached, the placeholders `{code}` and `What is the code?`, four invented web addresses, and codes not in the list (for example `Z88.0`, and `D1022` for `E1022`). In all, 20 of its answers carried text that is not a code in the list, and it answered 6 codes more than once, some with different categories.
-   **Some categories contradict the model's own reason or are clinically wrong.** Qwen put AIDS nephropathy (429) under Diabetes, with the reason that it "falls under viral/glomerular causes … not diabetes". Llama put lupus nephritis (7100) and membranous nephropathy (5831) under Diabetes, and malignant hypertension (4010) under Diabetes with the reason "No indication of diabetes".
-   **They were slow.** Qwen took 108 minutes for its answers; Llama about 2.5 minutes per batch of 5, close to four hours for the list. The cloud models took minutes.
-   **A third model did not run at all.** IBM's Granite (`granite4.2:8b`) timed out after 30 minutes on a batch of 25 codes, and returned no answers for 5 codes in 15 minutes; Llama replaced it.

These are observations from one laptop and one prompt, not a general verdict on local models; larger local models, a computer with a capable graphics card, or a prompt asking for fewer codes at a time might do better. `references/esrd-cause-local-models.csv` records, for each local model, how many codes it answered once with a code from the list, left unanswered or answered with other text, and how often it gave the category the cloud models accepted (`local_model_report()`, on the [functions page](functions.qmd)).

## How the mapping is checked

Agreement among the models shows only that they agree, not that they are right. The plan adds two checks on the data, run by an authorized person once the mapping is reviewed:

-   **Against USRDS's own grouping.** The USRDS PATIENTS file carries a primary disease group for each patient (`DISGRPC`). A cross-tabulation of the six categories against it, as percentages with small cells suppressed, shows which codes the mapping puts somewhere USRDS does not. Differences are expected where the definitions depart from the CMS grouping on purpose (secondary glomerulonephritis, HIV, heart failure); any others point to codes to review.
-   **Against the paper.** The cohort's share in each category, compared with the published Table 1 percentages above. A large gap in one category points to codes to review.
